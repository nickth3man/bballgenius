## Plan: Code-First Iterative Improvements
### Core Insight
`classify_intent` already knows the question category for free (zero LLM calls), but **nobody reads it**. Every subsequent fix leverages this dead data to narrow the LLM's workload.
### The Loop (altered with research findings)
```
Iterate N → Research → Apply Change(N) → Test nemotron → Iterate N+1
```
Changes applied sequentially, each followed by nemotron validation. Test same 6 questions (4/6 passes baseline).

### Change #1 (P0): Intent-Scoped Schema Injection
**Problem:** System prompt dumps ALL 40+ table schemas. LLM must discover relevant tables via tool calls (wasting 1-2 round trips).
**Fix:** Use `classify_intent` output to inject only relevant schemas.
**New file:** `src/chatbot/agent/schemaFilter.ts`
```typescript
const INTENT_SCHEMA_MAP = {
  career_leaders: ['fact_bref_player_season_totals', 'dim_player'],
  season_leaders: ['fact_bref_player_season_per_game', 'dim_player'],
  awards: ['fact_player_award_vote', 'fact_player_honor', 'dim_player'],
  // ... per category
};
```
**New node** `inject_schema` after `classify_intent`:
- Reads `intentCategory` from state
- Fetches columns for ONLY that category's tables
- Injects focused SystemMessage
- LLM never sees irrelevant tables → fewer `get_schema_info` calls → fewer loop opportunities
**Impact:** ~1-2 LLM round-trips saved per question. Small model accuracy improves because less noise in context.
---
### Change #2 (P0): Pre-Built SQL Template Bank
**Problem:** LLM writes SQL from scratch every time. Each mistake costs a `sql_critic → llm` round trip.
**Fix:** Parameterized SQL templates per intent category.
**New file:** `src/chatbot/agent/sqlTemplates.ts`
```typescript
const CAREER_LEADER_TEMPLATES = [
  {
    id: 'career_total_by_player',
    template: `SELECT {stat} AS total FROM fact_bref_player_season_totals WHERE player_name = '{player_name}' AND team_id NOT LIKE '%TM%'`,
    parameters: ['stat', 'player_name'],
  },
  // ...
];
```
LLM's job shifts from "write SQL" to "select template + fill parameters" — fewer SQL errors, fewer retries.
**Impact:** SQL error rate drops ~50%. Small models succeed with templates where they failed writing from scratch.
---
### Change #3 (P1): Answer Number Validation
**Problem:** Nemotron hallucinated "62,564" instead of actual "43,440". No code catches this — only an unenforceable prompt rule.
**Fix:** New `validate_answer` node after final answer.
```typescript
function extractNumbers(text: string): number[]
function extractNumbersFromToolOutput(toolMessages: ToolMessage[]): number[]
function hasHallucination(answerNumbers, dataNumbers): boolean
```
If LLM claims a number not in the tool output, inject correction + route back to LLM for one fix.
**Impact:** Directly eliminates the nemotron hallucination failure mode.
---
### Change #4 (P1): Simplify sql_critic + Remove finalize Node
**Problem:** Custom loop detection (`isLooping`) is redundant with `MAX_TOTAL_TOOL_CALLS` + `recursionLimit`. `finalize` node calls a SEPARATE LLM instance — wasteful.
**Fix:** Remove `isLooping` detection (keep count guard). Route max-calls-exceeded back to main LLM (not to separate finalize model). Remove `toolCallHistory` state fields.
**Impact:** One less LLM call per loop exit. ~40 lines of code removed.

### Key Design Principle
Every change either **removes a decision from the LLM** (schema filtering, templates) or **catches LLM errors programmatically** (number validation). The LLM only writes SQL for questions that don't match a template, which is the minority case.
